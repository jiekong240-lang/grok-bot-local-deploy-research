# [Grok Build](https://docs.x.ai/build/overview#grok-build)

[Create API key](https://console.x.ai/team/default/api-keys?utm_source=docs&utm_medium=referral&utm_campaign=build-overview&utm_content=article-api-key)[Meet grok-4.7](https://x.ai/news/grok-4-7)

Grok Build is a powerful and extensible coding agent. Use it via an interactive TUI, headlessly in scripts or bots, or through the Agent Client Protocol (ACP) in other apps.

The TUI provides a rich, mouse-interactive, fullscreen experience for coding with agents.

## [Install](https://docs.x.ai/build/overview#install)

macOS / Linux / WSLWindows (PowerShell)

```
curl -fsSL https://x.ai/cli/install.sh | bash
```

```
irm https://x.ai/cli/install.ps1 | iex
```

## [Start an interactive session](https://docs.x.ai/build/overview#start-an-interactive-session)

Bash

```
cd your-project
grok
```

On first launch, Grok opens a browser for authentication. In non-browser environments, use an API key:

Bash

```
export XAI_API_KEY="xai-..."
grok
```

Useful first prompts:

Text

```
Explain this repo.
@src/main.rs Walk me through this file.
```

## [Run headlessly](https://docs.x.ai/build/overview#run-headlessly)

Bash

```
grok -p "Explain this codebase"
grok -p "Explain the architecture" --output-format streaming-json
```

Headless usage is ideal for scripts, automations, or integration into other apps.

## [Custom models](https://docs.x.ai/build/overview#custom-models)

Grok supports any custom model. Add it to your user-level config file, `~/.grok/config.toml` (on Windows, `%USERPROFILE%\.grok\config.toml`):

Text

```
[model.my-model]
model = "model-id"
base_url = "https://api.example.com/v1"
name = "Display Name"
env_key = "API_KEY"

[models]
default = "my-model"
```

After updating `~/.grok/config.toml`, use `grok inspect` to see what Grok discovered in the current directory, including config sources, instructions, skills, plugins, hooks, and MCP servers, then pick the model in headless mode or in the TUI:

Bash

```
grok inspect
grok -p "Hello" -m my-model
```

You can also switch inside the TUI with `/model <name>`.

## [Use Grok 4.7 on the API](https://docs.x.ai/build/overview#use-grok-47-on-the-api)

[`grok-4.7`](https://docs.x.ai/developers/models/grok-4.7), SpaceXSI's latest model, is available directly on the xAI API. Drop it into your own agent loop, IDE integration, or coding tool.

JavaScriptPython (OpenAI)Bash Python

```
import { xai } from '@ai-sdk/xai';
import { generateText } from 'ai';

const { text } = await generateText({
  model: xai.responses('grok-4.7'),
  prompt: 'Fix this function and explain the bug: function median(a){a.sort();return a[a.length/2]}',
});

console.log(text);
```

```
from openai import OpenAI

client = OpenAI(
    api_key="<YOUR_XAI_API_KEY_HERE>",
    base_url="https://api.x.ai/v1",
)

response = client.responses.create(
    model="grok-4.7",
    input="Fix this function and explain the bug: function median(a){a.sort();return a[a.length/2]}",
)

print(response.output_text)
```

```
curl https://api.x.ai/v1/responses \

  -d '{
    "model": "grok-4.7",

```

# Getting started

Install OpenClaw, run onboarding, and chat with your AI assistant in about 5 minutes. By the end you will have a running Gateway, configured auth, and a working chat session.

## What you need

- **Node.js 24.16.0+ on 24.x, or 26.1.0+** (Node 26 is recommended; use 24.22.1+/26.12.1+ for the security fixes)
- **An existing Claude Code or Codex CLI login, or a provider API key** — onboarding can reuse it

**Tip**

Check your Node version with `node --version`. **Windows users:** the native Windows Hub app is the easiest desktop path. The PowerShell installer and WSL2 Gateway paths are also supported. See [Windows](https://docs.openclaw.ai/platforms/windows). Need to install Node? See [Node setup](https://docs.openclaw.ai/install/node).

## Try it in one command

bashCopy code

```bash
npx openclaw@latest
```

On a fresh install, choose **Quick start** after a one-line pointer to the [security guide](https://docs.openclaw.ai/gateway/security). That is the only onboarding prompt when usable AI access is already available: OpenClaw finds an existing Claude Code or Codex CLI login or API key, verifies it with a real completion, saves the config, and opens the web dashboard.

Quick start then asks **Keep OpenClaw running in the background?** Yes installs a copy of the same OpenClaw version under `~/.openclaw` and runs the Gateway as a background service from it, so clearing the npx cache does not stop it. No keeps the Gateway in this terminal until you press **Ctrl+C**; your config stays saved. If no detected route works, onboarding opens manual provider setup. Choose **Custom setup** to walk through all guided options instead.

To keep the Gateway running in the background later, install the CLI below and run `openclaw gateway install`, then `openclaw gateway start` to wait until it is ready. Run `openclaw` for the TUI or `openclaw dashboard` to reopen the web UI.

## Quick setup

### Install OpenClaw

### macOS / Linux

bashCopy code

```bash
curl -fsSL https://openclaw.ai/install.sh | bash
```

### Windows (PowerShell)

powershellCopy code

```powershell
iwr -useb https://openclaw.ai/install.ps1 | iex
```

**Note**

Other install methods (Docker, Nix, npm): [Install](https://docs.openclaw.ai/install).

### Complete onboarding

The installer starts the guided onboarding wizard automatically. Choose **Quick start** to reuse detected AI access and open the dashboard, or **Custom setup** for the full guided flow. Provider sign-in and optional setup can take longer. Return later with `openclaw configure` for additional settings. `openclaw onboard --classic` opens the classic step-by-step wizard instead.

See [Onboarding (CLI)](https://docs.openclaw.ai/start/wizard) for the full reference.

### Install the Gateway service

Quick start asks **Keep OpenClaw running in the background?** and installs the service when you accept, so skip this step in that case. Otherwise, press **Ctrl+C** to stop the foreground Gateway, then install the service and wait for it to be ready:

bashCopy code

```bash
openclaw gateway installopenclaw gateway start
```

This installs a LaunchAgent on macOS, a systemd user unit on Linux and WSL2, or a Scheduled Task on native Windows (with a per-user Startup-folder login item as the fallback if task creation is denied). Your config stays saved across the stop and the install.

`gateway install` returns once the service is registered, while the Gateway may still be starting. `gateway start` waits until the Gateway passes its health and readiness checks; it does not restart a Gateway that is already running.

### Verify the Gateway is running

bashCopy code

```bash
openclaw gateway status
```

You should see the Gateway listening on port 18789.

### Open the dashboard

bashCopy code

```bash
openclaw dashboard
```

This opens the Control UI in your browser. If it loads, everything is working.

### Send your first message

Type a message in the Control UI chat and you should get an AI reply.

Want to chat from your phone instead? The fastest channel to set up is [Telegram](https://docs.openclaw.ai/channels/telegram) (just a bot token). See [Channels](https://docs.openclaw.ai/channels) for all options.

Advanced: mount a custom Control UI build

If you maintain a localized or customized dashboard build, point `gateway.controlUi.root` to a directory that contains your built static assets and `index.html`.

bashCopy code

```bash
mkdir -p "$HOME/.openclaw/control-ui-custom"# Copy your built static files into that directory.
```

Then set:

jsonCopy code

```json
{  "gateway": {    "controlUi": {      "enabled": true,      "root": "${HOME}/.openclaw/control-ui-custom"    }  }}
```

Restart the gateway and reopen the dashboard:

bashCopy code

```bash
openclaw gateway restartopenclaw dashboard
```

## If setup does not work

One command turns the current state of your install into a diagnosis you can act on:

bashCopy code

```bash
openclaw triage
```

It runs read-only health checks, writes a sanitized prompt describing what it found, and then offers to hand that prompt to a coding agent it detects on your machine — Claude Code, Codex CLI, or the built-in OpenClaw agent — so the agent starts with the diagnosis already loaded. Pick "just print the commands" if you would rather run the handoff yourself.

Nothing leaves your machine until you choose an agent, and secrets, tokens, raw chat payloads, and raw logs are excluded from the prompt.

To read the findings yourself instead, run [`openclaw doctor`](https://docs.openclaw.ai/cli/doctor). For symptom-first routes, see [Troubleshooting](https://docs.openclaw.ai/help/troubleshooting).

# Ollama

OpenClaw talks to Ollama's native API (`/api/chat`), not the OpenAI-compatible `/v1` endpoint. Three setups are supported:

Setup What it uses Cloud + Local A reachable Ollama host, serving local models and (if signed in) `:cloud` models Local only A reachable Ollama host, local models only Ollama Cloud `https://ollama.com` directly through the `ollama-cloud` provider, no daemon

Hosted-only access is its own **Ollama Cloud** setup choice; see [Ollama Cloud](https://docs.openclaw.ai/providers/ollama-cloud). Its `ollama-cloud/<model>` refs keep cloud routing separate from the local `ollama` provider.

**Warning**

Do not use the `/v1` OpenAI-compatible URL (`http://host:11434/v1`). It breaks tool calling and models can emit raw tool-call JSON as plain text. Use the native URL: `baseUrl: "http://host:11434"` (no `/v1`).

The current config key is `baseUrl`. `baseURL` is also accepted for OpenAI-SDK-style examples, but new config should use `baseUrl`.

This page is an index. Ollama is documented on nine pages, one per reader job. Open the page that matches your task.

# Specification

[Model Context Protocol](https://modelcontextprotocol.io) (MCP) is an open protocol that enables seamless integration between LLM applications and external data sources and tools. Whether you’re building an AI-powered IDE, enhancing a chat interface, or creating custom AI workflows, MCP provides a standardized way to connect LLMs with the context they need. This specification defines the authoritative protocol requirements, based on the TypeScript schema in [schema.ts](https://github.com/modelcontextprotocol/specification/blob/main/schema/2026-07-28/schema.ts). For implementation guides and examples, visit [modelcontextprotocol.io](https://modelcontextprotocol.io). The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “NOT RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in [BCP 14](https://datatracker.ietf.org/doc/html/bcp14) [[RFC2119](https://datatracker.ietf.org/doc/html/rfc2119)] [[RFC8174](https://datatracker.ietf.org/doc/html/rfc8174)] when, and only when, they appear in all capitals, as shown here.

## [​](https://modelcontextprotocol.io/specification/2026-07-28#overview) Overview

MCP provides a standardized way for applications to:

- Share contextual information with language models
- Expose tools and capabilities to AI systems
- Build composable integrations and workflows

The protocol uses [JSON-RPC](https://www.jsonrpc.org/) 2.0 messages to establish communication between:

- **Hosts**: LLM applications that initiate connections
- **Clients**: Connectors within the host application
- **Servers**: Services that provide context and capabilities

MCP takes some inspiration from the [Language Server Protocol](https://microsoft.github.io/language-server-protocol/), which standardizes how to add support for programming languages across a whole ecosystem of development tools. In a similar way, MCP standardizes how to integrate additional context and tools into the ecosystem of AI applications.

## [​](https://modelcontextprotocol.io/specification/2026-07-28#key-details) Key Details

### [​](https://modelcontextprotocol.io/specification/2026-07-28#base-protocol) Base Protocol

- [JSON-RPC](https://www.jsonrpc.org/) message format
- Stateless, self-contained requests
- Per-request capability negotiation

### [​](https://modelcontextprotocol.io/specification/2026-07-28#features) Features

Servers offer any of the following features to clients:

- **Resources**: Context and data, for the user or the AI model to use
- **Prompts**: Templated messages and workflows for users
- **Tools**: Functions for the AI model to execute

Clients may offer the following features to servers:

- **Elicitation**: Server-initiated requests for additional information from users

### [​](https://modelcontextprotocol.io/specification/2026-07-28#additional-utilities) Additional Utilities

- Configuration
- Progress tracking
- Cancellation
- Error reporting

### [​](https://modelcontextprotocol.io/specification/2026-07-28#extensions) Extensions

Beyond the core protocol, MCP defines optional [extensions](https://modelcontextprotocol.io/extensions/overview) that add modular, specialized, or experimental functionality. Extensions are always opt-in and require explicit support from both client and server, negotiated during initialization. Notable extensions include:

- [**Tasks**](https://modelcontextprotocol.io/extensions/tasks/overview): Asynchronous execution of long-running operations, with polling, mid-flight input, and durable handles
- [**Skills over MCP**](https://modelcontextprotocol.io/community/working-groups/skills-over-mcp): Rich, structured instructions for agent workflows, discovered and consumed through MCP
- [**MCP Apps**](https://modelcontextprotocol.io/extensions/apps/overview): Interactive UI elements (charts, forms, video players) rendered inline within conversations

## [​](https://modelcontextprotocol.io/specification/2026-07-28#security-and-trust-&-safety) Security and Trust & Safety

The Model Context Protocol enables powerful capabilities through arbitrary data access and code execution paths. With this power comes important security and trust considerations that all implementors must carefully address.

### [​](https://modelcontextprotocol.io/specification/2026-07-28#key-principles) Key Principles

1. **User Consent and Control**
   
   - Users must explicitly consent to and understand all data access and operations
   - Users must retain control over what data is shared and what actions are taken
   - Implementors should provide clear UIs for reviewing and authorizing activities
2. **Data Privacy**
   
   - Hosts must obtain explicit user consent before exposing user data to servers
   - Hosts must not transmit resource data elsewhere without user consent
   - User data should be protected with appropriate access controls
3. **Tool Safety**
   
   - Tools represent arbitrary code execution and must be treated with appropriate caution.
     
     - In particular, descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server.
   - Hosts must obtain explicit user consent before invoking any tool
   - Users should understand what each tool does before authorizing its use

### [​](https://modelcontextprotocol.io/specification/2026-07-28#implementation-guidelines) Implementation Guidelines

While MCP itself cannot enforce these security principles at the protocol level, implementors **SHOULD**:

1. Build robust consent and authorization flows into their applications
2. Provide clear documentation of security implications
3. Implement appropriate access controls and data protections
4. Follow security best practices in their integrations
5. Consider privacy implications in their feature designs

Local model with auto-discovery

Ollama on the same machine as the Gateway, discovered automatically:

Small local model profile

Local Ollama models automatically use structured [Tool Search](https://docs.openclaw.ai/tools/tool-search) when `tools.toolSearch` is unset. This keeps optional capabilities available while loading their schemas only when needed. Setup does not enable lean mode. App, interactive CLI, and non-interactive setup use a 32,768-token runtime context, or the model's native window if smaller. The advertised native window is retained separately; known cloud routes keep their hosted context. Large file reads use OpenClaw's context-based paging. The native adapter preserves those text pages and their continuation instructions; structured fallback data is bounded separately. Bound any explicit context override to what the host can support:

json5Copy code

```json5
{  agents: {    entries: {      local: {        model: { primary: "ollama/gemma4" },      },    },  },  models: {    providers: {      ollama: {        baseUrl: "http://127.0.0.1:11434",        apiKey: "ollama-local",        api: "ollama",        models: [          {            id: "gemma4",            name: "gemma4",            input: ["text"],            contextTokens: 32768,            params: { num_ctx: 32768 },          },        ],      },    },  },}
```

Explicit `tools.toolSearch` settings take precedence, including `false`. Tool Search does not change Ollama's context or thinking mode. Ollama thinking defaults to off; an explicit thinking setting can change that independently. If you previously enabled `localModelLean`, set it to `false` to restore optional tools while retaining automatic Tool Search.

Use `compat.supportsTools: false` only when the model or server reliably fails on tool schemas; it disables tool use entirely. For a deliberately narrower agent, prefer `tools.profile` or a per-agent tool policy.

### Model selection

{  agents: {    defaults: {      model: {        primary: "ollama/gpt-oss:20b",        fallbacks: ["ollama/llama3.3", "ollama/qwen2.5-coder:32b"],      },    },  },}

# Ollama troubleshooting

## Troubleshooting

WSL2 crash loop (repeated reboots)

On WSL2 with NVIDIA/CUDA, the official Ollama Linux installer creates an `ollama.service` systemd unit with `Restart=always`. If that service autostarts and loads a GPU-backed model during WSL2 boot, Ollama can pin host memory while loading; Hyper-V memory reclaim cannot always reclaim those pages, so Windows can terminate the WSL2 VM, systemd restarts Ollama, and the loop repeats.

Evidence: repeated WSL2 reboots/terminations, high CPU in `app.slice` or `ollama.service` right after WSL2 startup, and SIGTERM from systemd rather than the Linux OOM killer.

OpenClaw logs a startup warning when it detects WSL2, `ollama.service` enabled with `Restart=always`, and visible CUDA markers.

Mitigation:

bashCopy code

```bash
sudo systemctl disable ollama
```

On the Windows side, add this to `%USERPROFILE%\.wslconfig`, then run `wsl --shutdown`:

iniCopy code

```ini
[experimental]autoMemoryReclaim=disabled
```

Or shorten keep-alive / start Ollama manually only when needed:

bashCopy code

```bash
export OLLAMA_KEEP_ALIVE=5mollama serve
```

See [ollama/ollama#11317](https://github.com/ollama/ollama/issues/11317).

Ollama not detected

Confirm Ollama is running and is in the agent's model scope. For ambient localhost discovery, set `OLLAMA_API_KEY` (or an auth profile). An explicit self-hosted endpoint is discovered whether or not it lists models:

bashCopy code

```bash
ollama servecurl http://localhost:11434/api/tags
```

No models available

Pull the model locally, or define it explicitly in `models.providers.ollama`:

bashCopy code

```bash
ollama list  # See what's installedollama pull gemma4ollama pull gpt-oss:20bollama pull llama3.3     # Or another model
```

Connection refused

bashCopy code

```bash
# Check if Ollama is runningps aux | grep ollama # Or restart Ollamaollama serve
```

Remote host works with curl but not OpenClaw

Verify from the same machine and runtime that runs the Gateway:

bashCopy code

```bash
openclaw gateway status --deepcurl http://ollama-host:11434/api/tags
```

Common causes:

- `baseUrl` points at `localhost`, but the Gateway runs in Docker or on another host.
- The URL uses `/v1`, selecting OpenAI-compatible behavior instead of native Ollama.
- The remote host needs firewall or LAN binding changes.
- The model is on your laptop's daemon but not the remote one.

Model outputs tool calls as text

Usually the provider is in OpenAI-compatible mode, or the model cannot handle tool schemas. Prefer native mode:

json5Copy code

```json5
{  models: {    providers: {      ollama: {        baseUrl: "http://ollama-host:11434",        api: "ollama",      },    },  },}
```

If a small local model still fails on tool schemas, set `compat.supportsTools: false` on that model entry and retest.

When a reply consists of a structured tool-call attempt naming an available tool, including wrapped XML, ReAct `Action`/`Action Input`, and legacy `[TOOL_CALL]` blocks, OpenClaw asks the model once to call the tool natively when recovery is safe. Earlier side effects can prevent that retry. A repeated text call fails visibly instead of reporting success. Text calls are never executed by this guard; examples in substantive answers remain text. The original reply and corrective continuation remain in session history.

If tool calls still arrive as text, try [llmman](https://docs.openclaw.ai/providers/llmman#advanced-configuration) with its explicit native Ollama configuration and a model that supports tool calling.

Repeated tool errors stop the turn

With `tools.toolSearch` unset, embedded runs using native local Ollama expose policy-approved `web_search`, `web_fetch`, `memory_search`, and `memory_get` directly. Other optional tools remain deferred. Explicit Tool Search settings keep their configured behavior. Direct exposure does not enable a denied tool, enable memory, or configure a web-search provider.

After three consecutive identical failures for the same tool and arguments, OpenClaw blocks that exact action and gives the model one chance to replan. An unchanged retry ends the turn without executing the call again. Unknown tool IDs also count. This protection is always active; enabling `tools.loopDetection` is not required.

Ollama 0.40's generic parser can mistake a chat-template marker for an advertised tool name. Tool Search uses the collision-free `dispatch_action` name across providers, with the same name in instructions, requests, and new session history. It no longer needs an `openclaw_tool_call` wire alias. Directly exposed names that still collide, such as `ls`, `name`, and `function`, retain transport-only aliases such as `openclaw_ls`. Execution and session history keep those tools' original names.

These remaining aliases cover native Ollama and the Ollama plugin's identified OpenAI-compatible chat-completions route. Other providers are unchanged. Custom Ollama templates with different markers may need separate diagnosis.

Check the named tool's inputs or service. If a failed action may have partly applied, inspect its state before choosing another action. If the model repeatedly invents tool names or cannot use exposed schemas, consider a model with native tool calling. Changed errors and successes reset the streak but do not release an already blocked action. A committed new user message starts a fresh recovery allowance. See [Tool-loop detection](https://docs.openclaw.ai/tools/loop-detection).

Repetitive output stopped

OpenClaw stopped a long repetition-dominated response from a model with a known total size in the 32B class or smaller. It replaced the affected unfinished block in session history with `[Repetitive output stopped]`. Earlier blocks and completed tool work remain; side effects are not retried automatically.

Try a stronger model, request less output, or split the task into smaller turns. Native Ollama requests also send the resolved model output cap as `num_predict`; lower the model's `maxTokens` if generation runs too long. Discovered local models default to 8,192 output tokens. Ollama Cloud models use their documented output limits, or their context window when a separate output limit is unavailable. Authored `maxTokens` and `params.num_predict` override those defaults. Set `params: { num_predict: -1 }` on a model entry to restore Ollama's unlimited generation default; an explicit request output cap still wins. The detector starts around 16,000 characters and can stop legitimate output with sufficiently dominant repetition. It applies to the 32B class (less than 34 billion total parameters) and stays off when total model size is unknown. See [Output budgets and repetition stops](https://docs.openclaw.ai/gateway/local-models#output-budgets-and-repetition-stops).

Kimi or GLM returns garbled symbols

Hosted Kimi/GLM responses that are long, non-linguistic symbol runs are treated as a failed provider call rather than a successful reply, so normal retry/fallback/error handling takes over instead of persisting corrupted text into the session.

If it recurs, capture the model name, the current session file, and whether the run used `Cloud + Local` or Ollama Cloud, then try a fresh session and a fallback model:

bashCopy code

```bash
openclaw infer model run --model ollama/kimi-k2.6:cloud --prompt "Reply with exactly: ok" --jsonopenclaw models set ollama/gemma4
```

Cold local model times out

Large local models can need a long first load. Scope the timeout to the Ollama provider and optionally keep the model loaded between turns:

json5Copy code

```json5
{  models: {    providers: {      ollama: {        timeoutSeconds: 300,        models: [          {            id: "gemma4:26b",            name: "gemma4:26b",            params: { keep_alive: "15m" },          },        ],      },    },  },}
```

If the host itself is slow to accept connections, `timeoutSeconds` also extends the guarded connect timeout for this provider.

Large-context model is too slow or runs out of memory

Many models advertise contexts larger than your hardware can run comfortably. Native requests forward the effective `contextTokens` unless `params.num_ctx` overrides it. Cap both OpenClaw's budget and Ollama's request context for predictable first-token latency:

json5Copy code

```json5
{  models: {    providers: {      ollama: {        maxTokens: 8192,        models: [          {            id: "qwen3.5:9b",            name: "qwen3.5:9b",            contextTokens: 32768,            params: { num_ctx: 32768, thinking: false },          },        ],      },    },  },}
```

Lower the model entry's `contextTokens` if OpenClaw sends too much prompt. Lower `params.num_ctx` if Ollama's runtime context is too large for the machine. Lower `maxTokens` if generation runs too long.

Memory embedding rebuild fails

If `openclaw memory index --force` fails against Ollama (for example with `bge-m3`), try [llmman](https://docs.openclaw.ai/providers/llmman#advanced-configuration) as the embedding server. `provider: "ollama"` only needs a new `remote.baseUrl`.

Ollama still aborts or hangs on this host

If `curl` to Ollama works but agent turns abort, try [llmman](https://docs.openclaw.ai/providers/llmman) as the local server.

# Configuration

OpenClaw reads an optional **JSON5** config from `~/.openclaw/openclaw.json`. If the file is missing, OpenClaw uses safe defaults.

Config writes require the active config path to be a regular file. Snapshot reads, including `backup create`, can follow a config-file symlink. The configured state directory may be a symlink: OpenClaw resolves its directory for atomic writes while retaining the configured path, and rejects a directory alias that changes during a write. To write config outside the default state directory, point `OPENCLAW_CONFIG_PATH` directly at the real file.

Common reasons to add a config:

- Connect channels and control who can message the bot
- Set models, tools, sandboxing, or automation (cron, hooks)
- Tune sessions, media, networking, or UI

See the [Configuration reference](https://docs.openclaw.ai/gateway/configuration-reference) for every available field.

Configuration follows a two-bucket rule: root siblings hold infrastructure and cross-agent defaults, while `agents.defaults` holds agent-loop behavior. Entries under `agents.entries` may override either bucket where the schema supports a per-agent override.

Agents and automation should use `config.schema.lookup` for exact field-level docs before editing config. Use this page for task-oriented guidance and [Configuration reference](https://docs.openclaw.ai/gateway/configuration-reference) for the broader field map and defaults.

**Tip**

**New to configuration?** Start with `openclaw onboard` for interactive setup, or check out the [Configuration Examples](https://docs.openclaw.ai/gateway/configuration-examples) guide for complete copy-paste configs.

## Strict validation

**Warning**

OpenClaw only accepts configurations that fully match the schema. Unknown keys, malformed types, or invalid values cause the Gateway to **refuse to start**. Run `openclaw doctor --fix` to repair legacy keys before starting the Gateway. The only root-level exception is `$schema` (string), so editors can attach JSON Schema metadata.

`openclaw config schema` prints the authoritative JSON Schema used by Control UI and validation. `config.schema.lookup` fetches a single path-scoped node plus child summaries for drill-down tooling. Field `title`/`description` docs metadata carries through nested objects, wildcard (`*`), array-item (`[]`), and `anyOf`/ `oneOf`/`allOf` branches. Runtime plugin and channel schemas merge in when the manifest registry is loaded.

Use `config.get` to read a redacted config snapshot without building the form schema. Request `config.schema` or `config.schema.lookup` when you need field metadata. The Gateway shares these results across clients and refreshes them when the active config or plugin generation changes.

Every config leaf has a common or advanced presentation tier in `uiHints`. `advanced: false` marks common settings and `advanced: true` marks advanced settings. A leaf inherits the nearest ancestor tier when it has no direct hint. Paths with no declared ancestor default to advanced. This affects presentation only, not validation, defaults, reload behavior, or whether the key can be set.

Startup migration uses the same fixed, prompt-free transforms as `openclaw doctor --fix` and writes only when the entire migrated config validates, including plugins. The previous config stays in the `.bak` ring. Configs using `$include`, Nix-managed configs, and configs written by a newer OpenClaw version are not automatically migrated. See [Legacy config key migrations](https://docs.openclaw.ai/gateway/doctor#detailed-behavior-and-rationale) for the conditions and fallback.

When validation still fails:

- `openclaw gateway run` reports the config issues and exits with code `78`, with SQLite or PostgreSQL state
- Only diagnostic commands work (`openclaw doctor`, `openclaw logs`, `openclaw health`, `openclaw status`)
- Run `openclaw doctor` to see exact issues
- Run `openclaw doctor --fix` (`--repair` is the same flag, and `--yes` skips prompts) to apply repairs

The Gateway keeps a trusted last-known-good copy after each successful startup, but startup and hot reload do not restore it automatically - only `openclaw doctor --fix` does. If `openclaw.json` remains invalid after eligible startup migrations (including plugin-local validation), Gateway startup fails. An invalid hot reload is skipped and the current runtime keeps the last accepted config. When a write is blocked as an accidental clobber, OpenClaw attempts to save the rejected payload as `<path>.rejected.<timestamp>` for inspection. The warning reports whether that save succeeded. If it failed, the active config still stays unchanged. The Gateway blocks writes that look like accidental clobbers - dropping the effective `gateway.mode` or shrinking the file by more than half - unless the write explicitly allows destructive changes. Mode checks resolve `$include` and environment references first. Missing `meta` is recorded as a write anomaly. Promotion to last-known-good is skipped when a candidate contains a redacted secret placeholder such as `***` or `[redacted]`. Suspicious external reductions and stub-shaped snapshots also leave the trusted recovery copy unchanged during startup and hot reload. An ordinary accepted edit to an already-truncated file does not approve that earlier loss for replacing the backup, so Doctor can still restore the intact configuration. The health owner carries that anomaly across automatic metadata stamping and later reads; stamping a missing `meta` section does not restore the lost settings.

- Installer 会报告 selected startup mode。
- Node hosts 保留 per-user interactive tasks 以支持 desktop access。
- 若需注册 boot tasks：从 elevated terminal 以 intended service user 运行安装。
- `openclaw doctor --fix` 可迁移 recognized older Gateway definitions 到 unattended startup，并在 repair 前备份 definition 和 launcher；custom definitions 保持 operator-owned。

5. 通过 service owner 停止 Gateway。
6. 替换 package。
7. 运行 newly installed Doctor。
8. 启动并验证 Gateway。

schtasks /create /tn "WSL Boot" /tr "wsl.exe -d Ubuntu --exec dbus-launch true" /sc onstart /ru "$env:USERNAME"
```

替换 `Ubuntu` 时使用：

```powershell
wsl --list --verbose
```

### After reboot：WSL 内验证

```bash
systemctl --user is-enabled openclaw-gateway.service
systemctl --user status openclaw-gateway.service --no-pager
```

## 1.6 Expose WSL services over LAN

WSL 有自己的 virtual network；若其他机器需要访问 WSL 内服务，需要把 Windows port 转发到当前 WSL IP。WSL IP 可能在重启后变化，因此需刷新 forwarding rule。

PowerShell as Administrator 示例：

```powershell
$Distro = "Ubuntu-24.04"
$ListenPort = 2222
$TargetPort = 22
$WslIp = (wsl -d $Distro -- hostname -I).Trim().Split(" ")[0]
if (-not $WslIp) { throw "WSL IP not found." }
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=$ListenPort `
  connectaddress=$WslIp connectport=$TargetPort
New-NetFirewallRule -DisplayName "WSL SSH $ListenPort" -Direction Inbound `
  -Protocol TCP -LocalPort $ListenPort -Action Allow
```

Notes：

- 其他机器 SSH 时目标是 Windows host IP，例如：`ssh user@windows-host -p 2222`。
- Remote nodes 必须指向 reachable Gateway URL，不能是 `127.0.0.1`。
- `listenaddress=0.0.0.0` 用于 LAN access；`127.0.0.1` 用于 local-only access。

# 3. 已知限制、注意事项与明确“不会/不能做”的行为

## 3.1 Windows Hub、node mode 与 MCP mode 限制

### 发布与安装限制

- Windows Hub 仅声明支持 **Windows 10 20H2+ and Windows 11**；页面未声明对更早 Windows 版本的支持。
- Windows Hub 独立发布；regular OpenClaw stable releases 会 mirror 一个 **pinned, release-validated** Windows Hub build，但该 mirror **can lag** newer standalone Hub release。
- 若 direct `releases/latest/download` link 404，需到 Windows Hub releases page 打开 newest stable release。
- Windows Hub 的 standalone release 可能比 OpenClaw stable mirror 更新。
- Windows Hub 的 **Set up locally** 使用 app-owned `OpenClawGateway` WSL distro，**does not export or mutate your existing Ubuntu distro**。
- Local setup 失败的常见原因包括：disabled WSL、blocked virtualization、stale app-owned WSL state、安装 Gateway package 时 network failure。
- 若 tray icon 不出现：在 Task Manager 检查 `OpenClaw.Tray.WinUI.exe`；若正在运行，打开 hidden tray-icons area 并 pin；否则从 Start menu 启动 **OpenClaw Companion**。
- Local setup log 可从 Windows Hub 打开，或检查：

```powershell
notepad "$env:LOCALAPPDATA\OpenClawTray\Logs\Setup\easy-setup-latest.txt"
```

### Node mode 与 pairing 限制

- Node commands 必须由 node declared、包含于 approved surface、并由 Gateway policy allowed 后才能运行。
- Gateway 只转发 node declares 且 server policy allows 的命令。
- **Device approval admits the connection only**。
- 两个 request IDs 是不同的：`deviceRequestId` 与 `nodeRequestId`。
- 初始 unapproved surface **has no effective commands**。
- 如果 node mode 因 manual pairing 暂停，需要 restart node mode 或 app 以重新连接；重连会创建 separate command-surface request。
- 在 pending expansion 期间，仍 declared 且 allowed 的 approved commands 仍可运行。
- SSH-verified 和 bootstrap enrollment 可自动批准 first surface；**trusted-network device approval alone does not**。
- Later command、capability 或 permission expansion **still requires approval**。
- Privacy-sensitive commands 如 `screen.record`、`camera.snap`、`camera.clip` 需要显式 `gateway.nodes.commands.allow` opt-in。
- 若 app 提示 pairing required，需要在 Gateway 上批准 operator 或 node request：

```powershell
openclaw devices list
openclaw devices approve <requestId>
```

- 如果 device 已有 token，审批后需从 Connections tab reconnect。
- For a node request：必须完成 separate command-surface approval；重启 paused node mode，然后 `openclaw nodes pending` 并批准 distinct node request ID。
- **Operator-device approval alone does not complete that node flow**。

### Local MCP mode 限制

- Local MCP server 仅在 **loopback** 上暴露。
- 启用后显示 loopback endpoint 和 bearer token。
- 可在 **without a running OpenClaw Gateway** 的情况下让 local MCP clients 驱动 Windows capabilities。
- 可与 Gateway node mode 同时开启，也可单独开启；模式矩阵见 1.1。

## 3.2 Tauri desktop app 限制

页面明确写道：

> “Local setup requires a signed Windows Bun runtime in the app's pinned release.”

以及：

> “Linux, macOS, and unsigned test binaries are never substituted for a Windows release runtime.”

具体限制：

- 若旧版 app 报告 **“This app does not include a signed Windows Gateway runtime”**，必须更新到带 signed Windows runtime 的 app release，或连接 remote Gateway。
- **Installing system Node.js does not change the bundled runtime's admission policy**。
- Remote connections 在该情况下仍可继续工作。
- signed runtime unavailable 时：更新 desktop app 到 Windows-enabled runtime release，或使用 remote Gateway。
- Linux、macOS、unsigned test binaries 不会被替代为 Windows release runtime。
- Download 或 installation failed：检查 internet connection 和 proxy，然后 retry local setup；error panel 保留 installer diagnostics。
- Gateway will not start：使用 tray 的 Gateway controls 并检查 `openclaw gateway status --json`。
- app-managed CLI launcher 是 `%USERPROFILE%\.openclaw\bin\openclaw.cmd`；若该目录不在 `PATH`，需用 full path 调用。
- Startup task denied：service owner 会报告是否注册了 task 或 logon fallback。
- Desktop updater 的 Tauri signature 验证独立于 Windows Authenticode；Installer Authenticode signing 需 release owner 单独启用。
- Windows 可能对 unsigned installer 显示 unknown-publisher warning。
- 页面在 Tauri 部分只列出 **Windows x64 NSIS installer**；未列出 Tauri 的 ARM64 Windows 资产。
- Closing window 只让 app 留在 tray；local Gateway 有独立 service lifecycle。

## 3.3 Native Windows CLI / Gateway / Scheduled Task / PowerShell 限制

### PowerShell 执行策略与 shim

- Windows PowerShell 的 effective execution policy 为 Restricted 时，bare `openclaw` 会解析到 npm 的 `openclaw.ps1` shim，并在 OpenClaw 启动前停止。
- 页面要求 **Leave the execution policy unchanged**。
- install 还包含同目录的 `openclaw.cmd`。
- 该 `openclaw.cmd` 是 npm global shim，**not the desktop app launcher at `%USERPROFILE%\.openclaw\bin\openclaw.cmd`**。
- 若错误指向不同 `openclaw.ps1` 路径，该目录就是 npm prefix；应运行旁边的 `openclaw.cmd`。
- Doctor 可能请求在 review repairs 时 pause managed Gateway；若接受，Doctor 结束时会恢复 previous service state。
- A new token 以及之后的 Gateway restart 会断开仍使用 previous secret 的 clients。

### S4U、权限与启动模式

页面明确写道：

> “S4U does not provide Windows network credentials or access to encrypted files; installations that need those capabilities can retain an operator-configured Password task.”

相关限制：

- Managed Gateway startup 使用 current user's S4U principal、boot/logon triggers、direct `cmd.exe` action。
- S4U 可在 login 前运行且不存储 password。
- 但 S4U **不提供 Windows network credentials 或 access to encrypted files**。
- 需要这些能力的安装可保留 operator-configured Password task。
- Reinstall 只刷新 launcher files，不替换 account、credentials、action、triggers。
- Agent exec 优先 native PowerShell 7 executable，fallback 到 Windows PowerShell 5.1。
- Inaccessible Microsoft Store app-execution aliases 会被跳过；它们在 S4U 且 PowerShell 运行于另一个 logon session 时可能以 `spawn EPERM` 失败。
- 若 unattended exec commands 需要 PowerShell 7 语法（如 `&&`），需用 MSI 或 ZIP 安装 PowerShell 7。
- Node hosts 保留 per-user interactive tasks 以支持 desktop access。
- 如果 account cannot be identified 或 task creation denied：desktop task 或 Startup-folder fallback **requires interactive logon**，且 **cannot provide unattended boot startup**。
- 注册 boot tasks 需从 elevated terminal 以 intended service user 运行安装。
- `openclaw doctor --fix` 只迁移 recognized older Gateway definitions；custom definitions 保持 operator-owned。

### `gateway.cmd`、launcher、task ownership

- 若向 `gateway.cmd` launch line 追加 output redirection，必须 quote entire target，例如：

```text
>> "%USERPROFILE%\.openclaw\logs\gateway-stdout.log" 2>&1
```

- Complete trailing redirections 会被排除在 process ownership checks 之外。
- Unquoted environment expansions 可能在 Gateway arguments 中留下 filename fragments。
- OpenClaw 会保留 ambiguous launcher commands，并 **refuses to terminate a listener whose ownership cannot be verified**。
- 需 quote target 后重试。
- Task launcher owns supervised Gateway process tree。
- 用 `schtasks /end /tn "OpenClaw Gateway"`、`Stop-ScheduledTask` 或 Task Scheduler 的 **End** 会终止 Gateway 及其 descendants。
- 更新旧安装后，如果 update 未刷新 launcher，需运行：

```powershell
openclaw gateway install --force
```

- pnpm global installs 的新 launchers 使用 verified stable `node_modules/openclaw` link，避免 package replacement 使其失效。
- 旧 launcher 若指向 deleted package generation，需从 current installation 运行 `openclaw gateway install --force` 重写 `gateway.cmd`。
- 不使用 `--force` 时，registered task 可能保持不变。
- Reinstalling managed Scheduled Task 会先 stop 和 settle previous process，再 publish/start replacement；同样适用于 both installations use Node 或仅 service arguments 改变的情况。
- Status 会用 registered command 验证 running process；同名同端口的 older process **does not prove the replacement is running**。
- Installation 保留 existing service lock 和 runtime-pin checks；changed task 或 launcher 会 **block replacement**。
- Ordinary installation failures 使用 service owner 的 recovery 恢复 previous definition 和 running policy，前提是 ownership 仍可验证。
- Update 期间 updater 保留 recovery ownership；若 recovery 无法确认，需先检查 reported Task Scheduler state 再重试。
- Scheduler takeover evidence 和 Startup login-item reprobes 使用 elapsed-time budgets；wall-clock corrections 不会延长或提前结束等待。
- Publication 接受 filesystem timestamp changes，前提是 launcher identity、permissions、contents 仍匹配。
- Reinstallation 会报告保留在 task script 旁的 `.task.xml.bak` 和 launcher `.bak` recovery files。

### Status、Doctor、deep inspection 的限制

- Gateway status 和 Doctor 读取 Scheduled Task 的 numeric current state，独立于 Windows display language 或 console code page。
- A previous task exit result **does not prove whether it is running now**。
- Queued 或 unknown tasks **do not count as safely stopped** for Doctor maintenance。
- 需通过 service owner 停止 queued task；若 inspection inaccessible，需先 restore Task Scheduler inspection permissions。
- Updates 和 service recovery 通过 Task Scheduler native API 修改 enabled state。
- Access-denied guidance 使用 numeric HRESULT，而不是 translated Windows error text。
- Uncertain disable 仍会尝试恢复 previous enabled state；confirmed permission denial 会保持 task unchanged 并 request elevation。
- Enabled-state changes 允许最多 60 seconds 给 Windows PowerShell cold startup。
- Strict maintenance inspection 只跟随 registered CMD 或 VBS launcher，或带 literal arguments 的 directly registered executable，并会 recheck captured definition。
- Runtime inspection 使用 registered command，而不是 default launcher。
- Direct executable inspection **does not grant ownership** 去重写 executable 或 task definition。
- Automatic update service management 将 custom actions 报告为 unavailable 并保持 untouched，因为无法 restore managed launcher。
- Environment expansion 和 ambiguous argument quoting 仍 **uninspectable**。
- Deep discovery 从 executable 或 launcher evidence 识别 OpenClaw 和 legacy helpers；unrelated task 的 display name alone **does not identify a service**。
- Standard 和 selected task names 只在 registered action 是 modern Gateway 时 suppress extra-service findings；legacy 和 Node actions 仍可见。
- Doctor 将 incomplete inspection 与 eligible for existing cleanup 的 services 分开报告。
- 对 rejected CMD launcher line：status/update warnings 报告 rejected rule 和 physical line number，且 counting blank lines and comments；diagnostics 会 omit launcher text and environment values。
- 被拒行需 review，并使用 literal values with a single Gateway command 后重试。
- Inspection 不修改 launcher，也不授权 rewrite custom behavior。
- `openclaw gateway status --deep` 和 `openclaw doctor --deep` 报告 current account Startup folder 中的 sibling profiles。
- 若其 Scheduled Task absent，selected modern Gateway fallback 会从 extra-service list 中省略。
- 每个 Startup file 即使与 task 同名，仍是 separate service definition。
- Inspection 跟随 exact file 和 captured Gateway script。
- Complete inventory 保留 unreadable 或 malformed Gateway launchers 的 errors；Doctor/status 只列出 successfully inspected extra services。
- Startup inspection hints 使用 exact file path，且 **do not grant Task Scheduler control over it**。
- Local builds 会用 installation's `dist` 检查这些 definitions 是否有 running Gateway；重建文件前需 stop matching Gateway。
- Doctor 和 deep status 提供 read-only `schtasks /Query` hints，包括 Node hosts。
- Discovery 在 inventory query、Startup directory scan、launcher inspection 之间共享一个 60-second budget；若超时，completed discoveries 仍可用，Doctor 会报告 some services could not be inspected。
- 选择通过 service owner removal 前，需 review registered command 和 purpose。
- Doctor 识别 2026.9.3 shipped 的 waiting VBS launcher；custom launcher behavior 仍保留 existing definition。
- Doctor 使用 Task Scheduler defaults 比较 task definitions；omitted `Enabled` element 意味着 task 和 logon trigger 均为 `true`，XML export differences 不会触发 drift warnings 或 failed refresh verification。
- Explicitly disabled tasks 和 triggers 仍会报告。
- Status/Doctor 容忍 scheduler-injected `UseUnifiedSchedulingEngine=true`；replacement verification 仍防止该值被 silently discarded。
- Task check 允许 Windows PowerShell inherit 或 create console，因为某些 PowerShell 5.1 hosts 在禁用 console creation 时无法 inspection。
- 从无 console 的 app 调用时可能短暂显示 console window。
- 无 explicit caller deadline 时，每个 check 允许最多 60 seconds 给 PowerShell cold startup；registration inspection 与 Startup-folder checks 共享 budget。
- Explicit inspection budgets 会替换 default allowance；其他 direct lifecycle commands 保留 existing limits。
- Access-denied 和 timeout results 是 inspection failures，**not proof that a task is absent**。
- Inspection 失败时，Doctor 和 update refusals 会包含 underlying check detail；empty response 会识别 exit code 并报告 PowerShell produced no output。
- Previous-Gateway readiness verification 中，每个 Scheduled Task runtime check 最多 5 seconds，或更短的 remaining budget。
- Other service inspections 保留 caller's budget，包括验证 runtime rebuild 安全的较长 allowance。
- Update preflight 使用 update 的 `--timeout` budget；registration 或 runtime timeout 会重试 complete strict inspection once。
- 若 inspection 仍 unavailable：update 报告 enforced budget 和 check detail，保留 recorded service definition，并 **skips automatic service restart**。
- 此时需先用 `openclaw gateway status --deep` inspect，再在 update 后手动 restart。
- Losing verified ownership after admission 会 block service mutation。

### Gateway startup、SQLite staging 与 antivirus

- Gateway startup 通过 Windows APIs 创建 private SQLite staging directories，不编译 C#，也不启动 PowerShell 处理 permissions。
- Owner、SYSTEM、Administrators 保留 full access；其他 inherited access 在 creation 时被移除。
- Update restart helpers 避免 runtime C# compilation 和 `Invoke-Expression`。
- 若 antivirus software 仍 interrupt start，报告中需包含 detection name 和 `openclaw gateway status --json` 输出。

### Scheduled Task troubleshooting 限制

- 若 registered 但 **DISABLED** task：`openclaw gateway status` 和 Doctor 会命名该 task 并显示 recovery command。
- 可运行 `openclaw gateway start` 或 `openclaw doctor --fix` 重新启用并启动 managed Gateway。
- 需使用与 installation 相同的 profile、state/config overrides。
- Recovery 会先验证 registered launcher 和 task ownership；foreign 或 unverifiable task 保持不变并给出解释。
- Disabled task 在重新启用前，不能 after login 或 reboot 自动启动。
- 若 Scheduled Task stops before Gateway is ready：运行 `openclaw gateway status --json` 并检查 local Gateway log。
- `gateway/task-supervisor` 记录 child exit code、signal、最后 8,192 characters of stderr，包括 Gateway logging 启动前的 failures。
- Child stdout is discarded。
- Failed child 或 supervisor exits nonzero；intentional clean stop exits zero。
- A successful task result alone **does not prove the Gateway is healthy**。
- Task Scheduler 的 `RestartOnFailure` policy 只重试 failed start conditions 或 action launches；**Do not rely on it** 来重启“成功启动后又因错误退出”的 Gateway，例如 occupied port。
- 应先修复 logged cause，再运行 `openclaw gateway start`。

## 3.4 WSL2、headless WSL 与 LAN 暴露限制

- WSL2 被描述为 most Linux-compatible Gateway runtime on Windows，但仍需 WSL/systemd 配置。
- Manual setup 需要 `wsl --install` 或显式 distro 安装，例如 `Ubuntu-24.04`。
- 必须在 WSL 内启用 `systemd=true` 并 `wsl --shutdown` 重启 WSL。
- WSL has its own virtual network；其他机器访问 WSL 内服务需 Windows port forwarding。
- WSL IP can change after restarts，因此需 refresh forwarding rule。
- Remote nodes 必须指向 reachable Gateway URL，不能是 `127.0.0.1`。
- `listenaddress=0.0.0.0` 用于 LAN access；`127.0.0.1` 只用于 local-only access。
- SSH 从其他机器连接时，目标是 Windows host IP，例如 `ssh user@windows-host -p 2222`。
- Expose WSL services 的 PowerShell 命令需 as Administrator 运行。
- Headless WSL setup 需要 `dbus-x11`、`loginctl enable-linger "$(whoami)"`、`openclaw gateway install`，以及 Windows Scheduled Task `"WSL Boot"`。
- `Ubuntu` 需替换为 `wsl --list --verbose` 得到的 distro name。
- WSL >= 2.6.1.0 存在 regression（microsoft/WSL #13416）：即使 linger enabled，最后一个 client 退出后 15–20 seconds 会 idle-terminate distro。
- 因此使用 `dbus-launch true` 而不是 `/bin/true`；`dbus-launch true` 作为 workaround 保持 child-of-init process alive（community discussion：microsoft/WSL #9245）。
- `/ru "$env:USERNAME"` 替代 `/ru SYSTEM`，因为 per-user WSL distros 默认对 SYSTEM account 不可见；若用 SYSTEM，task 看似运行但 distro 永不启动。
- 以自己账户运行可避免该问题；创建 task 时 Windows 会提示输入密码。
- Reboot 后需验证 `systemctl --user is-enabled openclaw-gateway.service` 和 `systemctl --user status openclaw-gateway.service --no-pager`。
- Windows Hub local setup 失败的常见原因包括 disabled WSL、blocked virtualization、stale app-owned WSL state、安装 Gateway package 时 network failure。

## 3.5 2026.9.4 Windows updater 限制

- Published 2026.9.4 Windows updater 在 service handoff 中保留 old database reader。
- 若 target migrates shared state beyond schema 17，activation 后 callback 可能失败。
- 在 running 9.4 update 期间，candidate package lifecycle 会让 Doctor's read-only preflight 在 updater driver 未确认 stopped 时拒绝该 migration。
- Failed npm stage 会在 old updater 进入 repair 前保留 original package 和 Gateway。
- CLI preflight 在 package scripts skipped 时仍保留该检查；后续 refusal 可能被 old repair path 的 cleanup error 掩盖。
- 页面明确说该 containment **does not complete the automatic update**。
- 需等待 updater 退出并 review result。
- 升级需 verified backup + independent shell 中 manual package-manager procedure。
- 必须保留 original service account、package prefix、profile、state/config overrides。
- 替换 package 前需通过 owner 停止 Gateway。
- 替换后运行 newly installed Doctor，再启动并验证 Gateway。
- **Do not lower schema markers or run an older build against migrated data**。

# 4. 最需要优先关注的限制清单

1. **Windows Hub**：只声明支持 Windows 10 20H2+ / Windows 11；signed x64/ARM64 installers；无需 admin；本地 setup 不改动已有 Ubuntu，但依赖 WSL/virtualization/network。
2. **Tauri backup**：local setup 强制要求 signed Windows Bun runtime；system Node.js 不改变该策略；Linux/macOS/unsigned test binaries 不会替代 Windows runtime；文档只列 Windows x64 NSIS installer。
3. **PowerShell installer**：执行策略受限时不要改 execution policy，改用 npm `openclaw.cmd`。
4. **Native Gateway Scheduled Task**：S4U 可 before login 运行，但不提供 Windows network credentials 或 encrypted files access；fallback startup 不能提供 unattended boot startup。
5. **Node mode / MCP**：pairing、command-surface approval、policy allow、explicit opt-in 缺一不可；privacy-sensitive commands 需 `gateway.nodes.commands.allow`；local MCP server 仅 loopback。

## [ACP](https://docs.x.ai/build/cli/headless-scripting#acp)

Use ACP when you want IDE or tool integration rather than a terminal session.

Bash

```
grok agent stdio
```

This runs Grok as an ACP agent over JSON-RPC on stdin/stdout. The example below assumes `grok` is already authenticated locally, or `XAI_API_KEY` is set. `session/prompt` returns completion metadata; the assistant text itself arrives as `session/update` chunks.

JavaScript

```
import { spawn } from "node:child_process";
import readline from "node:readline";
import process from "node:process";

const proc = spawn("grok", ["agent", "stdio"], { stdio: ["pipe", "pipe", "pipe"] });
const rl = readline.createInterface({ input: proc.stdout });
const pending = new Map();
let nextId = 1;
let text = "";

proc.stderr.on("data", chunk => process.stderr.write(chunk));

rl.on("line", line => {
  const message = JSON.parse(line);

  if (message.method === "session/update") {
    const update = message.params?.update;
    if (update?.sessionUpdate === "agent_message_chunk" && update.content?.text) {
      text += update.content.text;
    }
    return;
  }

  const pendingRequest = pending.get(message.id);
  if (!pendingRequest) return;

  pending.delete(message.id);
  if (message.error) {
    pendingRequest.reject(new Error(message.error.message ?? JSON.stringify(message.error)));
  } else {
    pendingRequest.resolve(message.result ?? {});
  }
});

function request(method, params, timeoutMs = 30000) {
  const id = nextId++;

  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      pending.delete(id);
      reject(new Error(`${method} timed out`));
    }, timeoutMs);

    pending.set(id, {
      resolve(result) {
        clearTimeout(timer);
        resolve(result);
      },
      reject(error) {
        clearTimeout(timer);
        reject(error);
      },
    });

    proc.stdin.write(JSON.stringify({ jsonrpc: "2.0", id, method, params }) + "\n");
  });
}

const sleep = ms => new Promise(resolve => setTimeout(resolve, ms));

try {
  const init = await request("initialize", {
    protocolVersion: 1,
    clientCapabilities: {
      fs: { readTextFile: true, writeTextFile: true },
      terminal: true,
    },
  });

  const authMethods = new Set((init.authMethods ?? []).map(method => method.id));
  const methodId =
    process.env.XAI_API_KEY && authMethods.has("xai.api_key")
      ? "xai.api_key"
      : authMethods.has("cached_token")
        ? "cached_token"
        : null;

  if (!methodId) {
    throw new Error("Run `grok login` first, or set XAI_API_KEY.");
  }

  await request("authenticate", { methodId, _meta: { headless: true } });

  const { sessionId } = await request("session/new", {
    cwd: process.cwd(),
    mcpServers: [],
  });

  const prompt = await request("session/prompt", {
    sessionId,
    prompt: [{ type: "text", text: "Say hello in one short sentence." }],
  });

  let lastLength = -1;
  let stableChecks = 0;
  while (stableChecks < 2) {
    await sleep(150);
    if (text.length === lastLength) {
      stableChecks += 1;
    } else {
      lastLength = text.length;
      stableChecks = 0;
    }
  }

  console.log(text.trim() || `No text returned (stopReason=${prompt.stopReason})`);
} finally {
  rl.close();
  proc.kill();
}
```

- Number of Attention Heads (GQA): 32 for Q and 8 for KV
- Context Length: 32,768 natively and [131,072 tokens with YaRN](https://huggingface.co/Qwen/Qwen3-8B#processing-long-texts).

For more details, including benchmark evaluation, hardware requirements, and inference performance, please refer to our [blog](https://qwenlm.github.io/blog/qwen3/), [GitHub](https://github.com/QwenLM/Qwen3), and [Documentation](https://qwen.readthedocs.io/en/latest/).

## [](https://huggingface.co/Qwen/Qwen3-8B#quickstart)Quickstart

The code of Qwen3 has been in the latest Hugging Face `transformers` and we advise you to use the latest version of `transformers`.

With `transformers<4.51.0`, you will encounter the following error:

```
KeyError: 'qwen3'
```

The following contains a code snippet illustrating how to use the model generate content based on given inputs.

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "Qwen/Qwen3-8B"

# load the tokenizer and the model
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype="auto",
    device_map="auto"
)

# prepare the model input
prompt = "Give me a short introduction to large language model."
messages = [
    {"role": "user", "content": prompt}
]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    enable_thinking=True # Switches between thinking and non-thinking modes. Default is True.
)
model_inputs = tokenizer([text], return_tensors="pt").to(model.device)

# conduct text completion
generated_ids = model.generate(
    **model_inputs,
    max_new_tokens=32768
)
output_ids = generated_ids[0][len(model_inputs.input_ids[0]):].tolist() 

# parsing thinking content
try:
    # rindex finding 151668 (</think>)
    index = len(output_ids) - output_ids[::-1].index(151668)
except ValueError:
    index = 0

thinking_content = tokenizer.decode(output_ids[:index], skip_special_tokens=True).strip("\n")
content = tokenizer.decode(output_ids[index:], skip_special_tokens=True).strip("\n")

print("thinking content:", thinking_content)
print("content:", content)
```

## [](https://huggingface.co/Qwen/Qwen3-8B#switching-between-thinking-and-non-thinking-mode)Switching Between Thinking and Non-Thinking Mode

> The `enable_thinking` switch is also available in APIs created by SGLang and vLLM. Please refer to our documentation for [SGLang](https://qwen.readthedocs.io/en/latest/deployment/sglang.html#thinking-non-thinking-modes) and [vLLM](https://qwen.readthedocs.io/en/latest/deployment/vllm.html#thinking-non-thinking-modes) users.

### [](https://huggingface.co/Qwen/Qwen3-8B#enable_thinkingtrue)`enable_thinking=True`

By default, Qwen3 has thinking capabilities enabled, similar to QwQ-32B. This means the model will use its reasoning abilities to enhance the quality of generated responses. For example, when explicitly setting `enable_thinking=True` or leaving it as the default value in `tokenizer.apply_chat_template`, the model will engage its thinking mode.

```python
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    enable_thinking=True  # True is the default value for enable_thinking
)
```

In this mode, the model will generate think content wrapped in a `<think>...</think>` block, followed by the final response.

> For thinking mode, use `Temperature=0.6`, `TopP=0.95`, `TopK=20`, and `MinP=0` (the default setting in `generation_config.json`). **DO NOT use greedy decoding**, as it can lead to performance degradation and endless repetitions. For more detailed guidance, please refer to the [Best Practices](https://huggingface.co/Qwen/Qwen3-8B#best-practices) section.

### [](https://huggingface.co/Qwen/Qwen3-8B#enable_thinkingfalse)`enable_thinking=False`

We provide a hard switch to strictly disable the model's thinking behavior, aligning its functionality with the previous Qwen2.5-Instruct models. This mode is particularly useful in scenarios where disabling thinking is essential for enhancing efficiency.

```python
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    enable_thinking=False  # Setting enable_thinking=False disables thinking mode
)
```

In this mode, the model will not generate any think content and will not include a `<think>...</think>` block.

> For non-thinking mode, we suggest using `Temperature=0.7`, `TopP=0.8`, `TopK=20`, and `MinP=0`. For more detailed guidance, please refer to the [Best Practices](https://huggingface.co/Qwen/Qwen3-8B#best-practices) section.

### [](https://huggingface.co/Qwen/Qwen3-8B#advanced-usage-switching-between-thinking-and-non-thinking-modes-via-user-input)Advanced Usage: Switching Between Thinking and Non-Thinking Modes via User Input

We provide a soft switch mechanism that allows users to dynamically control the model's behavior when `enable_thinking=True`. Specifically, you can add `/think` and `/no_think` to user prompts or system messages to switch the model's thinking mode from turn to turn. The model will follow the most recent instruction in multi-turn conversations.

Here is an example of a multi-turn conversation:

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

class QwenChatbot:
    def __init__(self, model_name="Qwen/Qwen3-8B"):
        self.tokenizer = AutoTokenizer.from_pretrained(model_name)
        self.model = AutoModelForCausalLM.from_pretrained(model_name)
        self.history = []

    def generate_response(self, user_input):
        messages = self.history + [{"role": "user", "content": user_input}]

        text = self.tokenizer.apply_chat_template(
            messages,
            tokenize=False,
            add_generation_prompt=True
        )

        inputs = self.tokenizer(text, return_tensors="pt")
        response_ids = self.model.generate(**inputs, max_new_tokens=32768)[0][len(inputs.input_ids[0]):].tolist()
        response = self.tokenizer.decode(response_ids, skip_special_tokens=True)

        # Update history
        self.history.append({"role": "user", "content": user_input})
        self.history.append({"role": "assistant", "content": response})

        return response

# Example Usage
if __name__ == "__main__":
    chatbot = QwenChatbot()

    # First input (without /think or /no_think tags, thinking mode is enabled by default)
    user_input_1 = "How many r's in strawberries?"
    print(f"User: {user_input_1}")
    response_1 = chatbot.generate_response(user_input_1)
    print(f"Bot: {response_1}")
    print("----------------------")

    # Second input with /no_think
    user_input_2 = "Then, how many r's in blueberries? /no_think"
    print(f"User: {user_input_2}")
    response_2 = chatbot.generate_response(user_input_2)
    print(f"Bot: {response_2}") 
    print("----------------------")

    # Third input with /think
    user_input_3 = "Really? /think"
    print(f"User: {user_input_3}")
    response_3 = chatbot.generate_response(user_input_3)
    print(f"Bot: {response_3}")
```

> For API compatibility, when `enable_thinking=True`, regardless of whether the user uses `/think` or `/no_think`, the model will always output a block wrapped in `<think>...</think>`. However, the content inside this block may be empty if thinking is disabled. When `enable_thinking=False`, the soft switches are not valid. Regardless of any `/think` or `/no_think` tags input by the user, the model will not generate think content and will not include a `<think>...</think>` block.

## [](https://huggingface.co/Qwen/Qwen3-8B#processing-long-texts)Processing Long Texts

Qwen3 natively supports context lengths of up to 32,768 tokens. For conversations where the total length (including both input and output) significantly exceeds this limit, we recommend using RoPE scaling techniques to handle long texts effectively. We have validated the model's performance on context lengths of up to 131,072 tokens using the [YaRN](https://arxiv.org/abs/2309.00071) method.

YaRN is currently supported by several inference frameworks, e.g., `transformers` and `llama.cpp` for local use, `vllm` and `sglang` for deployment. In general, there are two approaches to enabling YaRN for supported frameworks:

- Modifying the model files: In the `config.json` file, add the `rope_scaling` fields:
  
  ```json
  {
      ...,
      "rope_scaling": {
          "rope_type": "yarn",
          "factor": 4.0,
          "original_max_position_embeddings": 32768
      }
  }
  ```
  
  For `llama.cpp`, you need to regenerate the GGUF file after the modification.
- Passing command line arguments:
  
  For `vllm`, you can use
  
  ```shell
  vllm serve ... --rope-scaling '{"rope_type":"yarn","factor":4.0,"original_max_position_embeddings":32768}' --max-model-len 131072  
  ```
  
  For `sglang`, you can use
  
  ```shell
  python -m sglang.launch_server ... --json-model-override-args '{"rope_scaling":{"rope_type":"yarn","factor":4.0,"original_max_position_embeddings":32768}}'
  ```
  
  For `llama-server` from `llama.cpp`, you can use
  
  ```shell
  llama-server ... --rope-scaling yarn --rope-scale 4 --yarn-orig-ctx 32768
  ```

> If you encounter the following warning
> 
> ```
> Unrecognized keys in `rope_scaling` for 'rope_type'='yarn': {'original_max_position_embeddings'}
> ```
> 
> please upgrade `transformers>=4.51.0`.

> All the notable open-source frameworks implement static YaRN, which means the scaling factor remains constant regardless of input length, **potentially impacting performance on shorter texts.** We advise adding the `rope_scaling` configuration only when processing long contexts is required. It is also recommended to modify the `factor` as needed. For example, if the typical context length for your application is 65,536 tokens, it would be better to set `factor` as 2.0.

> The default `max_position_embeddings` in `config.json` is set to 40,960. This allocation includes reserving 32,768 tokens for outputs and 8,192 tokens for typical prompts, which is sufficient for most scenarios involving short text processing. If the average context length does not exceed 32,768 tokens, we do not recommend enabling YaRN in this scenario, as it may potentially degrade model performance.

> The endpoint provided by Alibaba Model Studio supports dynamic YaRN by default and no extra configuration is needed.

## [](https://huggingface.co/Qwen/Qwen3-8B#best-practices)Best Practices

To achieve optimal performance, we recommend the following settings:

1. **Sampling Parameters**:
   
   - For thinking mode (`enable_thinking=True`), use `Temperature=0.6`, `TopP=0.95`, `TopK=20`, and `MinP=0`. **DO NOT use greedy decoding**, as it can lead to performance degradation and endless repetitions.
   - For non-thinking mode (`enable_thinking=False`), we suggest using `Temperature=0.7`, `TopP=0.8`, `TopK=20`, and `MinP=0`.
   - For supported frameworks, you can adjust the `presence_penalty` parameter between 0 and 2 to reduce endless repetitions. However, using a higher value may occasionally result in language mixing and a slight decrease in model performance.
2. **Adequate Output Length**: We recommend using an output length of 32,768 tokens for most queries. For benchmarking on highly complex problems, such as those found in math and programming competitions, we suggest setting the max output length to 38,912 tokens. This provides the model with sufficient space to generate detailed and comprehensive responses, thereby enhancing its overall performance.
3. **Standardize Output Format**: We recommend using prompts to standardize model outputs when benchmarking.
   
   - **Math Problems**: Include "Please reason step by step, and put your final answer within \boxed{}." in the prompt.
   - **Multiple-Choice Questions**: Add the following JSON structure to the prompt to standardize responses: "Please show your choice in the `answer` field with only the choice letter, e.g., `"answer": "C"`."
4. **No Thinking Content in History**: In multi-turn conversations, the historical model output should only include the final output part and does not need to include the thinking content. It is implemented in the provided chat template in Jinja2. However, for frameworks that do not directly use the Jinja2 chat template, it is up to the developers to ensure that the best practice is followed.

# Skill Injection Attribution

[](https://github.com/wanyichen06/skill-injection-attribution#skill-injection-attribution)

**Attributing Structured-Output Gains in Function Calling: Interface Alignment versus Procedural Transfer**

**Accepted to Findings of EMNLP 2026.** This is the compact public artifact for the accepted paper.

中文文档见 [README_CN.md](https://github.com/wanyichen06/skill-injection-attribution/blob/main/README_CN.md)。

## What this artifact tests

[](https://github.com/wanyichen06/skill-injection-attribution#what-this-artifact-tests)

Function-calling scores combine two properties:

1. selecting the correct tool and arguments; and
2. expressing the call in the wrapper format expected by the evaluator.

This artifact provides the scorer and hand-written controls used to separate these effects. The paper's central diagnostic is simple: if a format-only instruction reproduces a gain, the gain should not be described as evidence of portable procedural transfer without additional controls.

## What is included

[](https://github.com/wanyichen06/skill-injection-attribution#what-is-included)

```
src/
  evaluator.py          # JSON parsing and BFCL-style AST checks
  rescore_canonical.py  # standard vs. canonicalized rescoring
controls/
  format_only/          # explicit output-contract controls
  alias_only/           # wrapper-key controls
  wrong_alias/          # negative alias control
  schema_only/          # schema-only control
  schema_example/       # schema-plus-example control
  neutral_matched/      # length-matched neutral control
```

The public package intentionally contains method code and hand-written control templates only. It does **not** include model-generated skills, raw model outputs, benchmark manifests, per-item result dumps, or intermediate analysis files.

## Quick start

[](https://github.com/wanyichen06/skill-injection-attribution#quick-start)

```
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

To rescore a directory of BFCL-style JSON files:

```
python src/rescore_canonical.py \
  --results-dir /path/to/bfcl_v2_results \
  --output /path/to/rescoring_analysis.json
```

Each input JSON file should contain records with `model`, `condition`, `prediction`, and `ground_truth` fields. The script reports standard scoring, canonicalized scoring, wrapper-key frequencies, and paired bootstrap summaries. Canonicalization is intentionally narrow: it normalizes wrapper-key aliases that preserve the same function-call structure; it is not a complete semantic executor or an official leaderboard rescore.

## Paper and scope

[](https://github.com/wanyichen06/skill-injection-attribution#paper-and-scope)

- **Venue:** Findings of EMNLP 2026 (accepted)
- **Authors:** Wanyi Chen, Daoyuan Chen, Fang Kong
- **Paper:** [arXiv:2607.02595](https://arxiv.org/abs/2607.02595)
- **English paper:** [README_EN.md](https://github.com/wanyichen06/skill-injection-attribution/blob/main/README_EN.md)

The paper evaluates BFCL-style structured output primarily, with API-Bank as a cross-contract diagnostic and MATH-500/MultiHop-RAG as scope checks. Reported numbers and the interpretation of each diagnostic are in the paper; this repository is the compact method release.
